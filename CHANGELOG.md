# Agentimus — changelog

The full release history. The readme.txt shipped to WordPress.org keeps only
the most recent releases (its Changelog section has a 5,000-word cap); this
file is the complete record.

## 1.51.1
* Security: a connection key, or an approved assistant's access token, was accepted on two neighbouring admin routes and not only at the MCP endpoint it was issued for. The check asked whether the requested route *started with* `/agentimus/v1/mcp`, and `/agentimus/v1/mcp-token` — the route the settings screen uses to create the key — starts with it. A request there in WordPress's plain `?rest_route=` form seated the key as the administrator who created it, and one request could mint a write key from a read-only one whenever agent writes were switched on; the new key then passed every write check honestly. Reported by Ananda Dhakal of Patchstack. The route is now matched exactly, in every form WordPress accepts — the pretty path, the `?rest_route=` query, and the same field in a form body, which WordPress reads before either — and a second check holds every plugin credential to the route WordPress actually dispatched, refusing it anywhere else before that route's own permission check can mistake it for the owner's session. Exploiting it needed the MCP server switched on and a valid key or approved grant in hand. If you are not sure who holds a read-only key, create a new one; that retires the old one.

## 1.51.0
* New: every long list turns the same way now — the Request Log, Agent Access, the content worklist and the Google Index card all carry one numbered pager, replacing two Older/Newer walks and two private number strips that had grown independently. The strip keeps a constant seven slots whatever the page count, so it never changes width and a button never shifts under your pointer between clicks. The Request Log's Network column joins the sortable ones, and its refresh button no longer quietly resets you to page one — it had been passing a paging cursor the endpoint never took.
* Improved: one language for links across the plugin. A link inside a sentence wears a quiet underline at rest, because colour cannot be the only thing that says "clickable" when a status word can paint the identical colour beside it — an underline that arrives only on hover tells a touch user nothing at all. A jump to another screen ends in a small drawn chevron; a button that acts in place — Refresh, Purge edge cache, Re-check, Copy, Clear — answers your pointer with a soft highlight instead of an underline promising a destination it does not have; and every link that leaves your site keeps its small outward arrow. The score rail keeps its typed arrows — against its mono type, the typed glyph is the one that belongs. The Search Console and Bing Webmaster links on the Visibility screens also stop wearing a blue no other part of the plugin uses, and the Cloudflare panel's closing note now simply says "Open Cloudflare dashboard" on a link that cannot break across lines.
* Fixed: a description derived from a post's opening paragraph was cut wherever the word budget ran out — mid-clause, and at the length cap sometimes mid-word — and that line is served: the meta description, the structured data and the page's markdown twin all carry it. It now ends at a sentence boundary when whole sentences fit, pulls back to a clause with an honest ellipsis when one enormous sentence leaves no boundary, and never lets a tiny first sentence shrink the whole summary to itself. A long manual excerpt over the cap gets the same treatment instead of a mid-word chop.
* Fixed: editing a category or tag description never cleared that archive page at your CDN. A publish purges the pages it changes, but a term edit saves no post, so nothing fired and the edge kept serving the old archive for the rest of its cache life — describing every term on a site in one sitting left every one of those pages stale. The term's archive page is purged now, on edit and on delete, edge-only like the other listing purges.
* Fixed: acting on a review-bell card — Ignore, Allow, Block or Re-check — made the Dashboard's "Who Reached Your Site" and "What Your Site Runs" cards flash back to their first-load loading state. The action endpoints returned a slimmer activity payload than the one the Dashboard reads, and the screen replaces its whole activity object with what an action returns; every route that answers with activity now assembles the identical payload, pinned by a test that derives both sides.
* Fixed: one refusal path recorded nothing — a proven impostor turned away at a .well-known document vanished from the Request Log while the same refusal at llms.txt was written down. Every refusal leaves its line now.
* Improved: the review bell's "New" chip says what actually happens when the window closes — the card disappears, the client is not removed — and the readiness ladder's rung lines name who does what: crawlers reach and fetch, AI assistants read and cite.

## 1.50.1
* Fixed: the "Put this away" control is gone from the Findings screen — the whole feature, not just the link. Putting a suggestion away resolved nothing: it re-filed the row into a fold at the foot of the same screen, a collapsible in disguise. And only "when you have time" rows carried the control, so part of the list arrived offering to be dismissed while the rest did not — a difference meant as a trust rule that read as inconsistency. A list either folds as a whole or stands as a whole. Everything left together: the link, the "suggestions you put away" ledger, the endpoint behind them, the stored ids, and the put-away field a connected assistant used to read. Anything an owner had put away simply returns to the list.
* Improved: the Dashboard opens with its four small tiles — providers, capabilities, APIs, tools — and the Today card now sits directly above the full-width cards it belongs with. The tile row used to sit between Today and the rest, cutting the run of cards in two; now the small row leads, and Today, What Your Site Runs, the audience and the activity read as one consecutive group.

## 1.50.0
* New: you can write your own robots.txt rules from the Crawler Policy card. A plain text box is appended to the end of the generated file, exactly as written — appended, never replacing, so an edit cannot break the Content-Signal line or the crawler blocks the plugin writes, and clearing the box is the whole reset. The live robots.txt is shown right above the box, fetched from your site exactly as a crawler receives it — which also honestly shows when a robots.txt file on disk or an SEO plugin owns the job instead (then the extra rules do not apply, and the box says so), and warns when your server wraps the file in an error code, which a strict crawler may ignore. Write your own Sitemap line and the plugin stops adding its own rather than printing two.
* New: the review bell's cards now say why a visitor is unchecked, instead of one blank "not verified" covering every case. Each card names its own cause — identity checking is turned off, this bot cannot be checked because its operator publishes nothing to check against, its visits gave no clear answer yet, or it carries a real cryptographic signature from an operator this site does not know. Each cause reads differently on the card, so you can tell at a glance which unchecked rows are waiting for an answer and which will never have one — and the small info icon carries the full reason.
* New: each recommendation on a review card is now a small labelled chip that names the kind of action it asks for — nothing left to do, one plugin setting, or a rule at your host or CDN — with the full advice shown on hover. Three cards used to read as three similar sentences; now you can see before reading a word that one asks nothing of you, one is a click in Settings, and one needs your hosting panel. The cards are several lines shorter, and on a proven impostor the genuine engine's verified traffic is counted right in the stats line so the fake never wears the real crawler's numbers.
* New: the Client Decisions dialog opens each list with a plain notice saying what your decision actually reaches. A block is enforced at this plugin's machine files — llms.txt, the markdown pages, discovery — not across your whole site, and it is separate from robots.txt, which is only a request a bot may ignore. Trusting a client sends nothing to the bot and changes nothing in robots.txt. When blocking is switched off in Settings, the Blocked list says so instead of quietly presenting rules that are not being enforced. And a trusted client whose name is also on the robots.txt block list now says so on its row — trusted at the door but publicly asked to stay away can be exactly what you meant, but the two may only disagree out loud.
* Fixed: the review panel could advise turning on "Verify bot identities" when it was already on — the nudge showed for any unchecked row that claimed a checkable bot, whether or not the setting was enabled. It now knows the setting's live state and only suggests what would actually change something. The same fault was in the forged-signature card, which could recommend "turn on blocking" while blocking was already on; it now says the next attempt will be refused automatically.
* Fixed: a valid signature from an operator this plugin does not recognise displayed as "Passed" in a card's details, indistinguishable from a recognised operator's. Proof of identity is not a reason to trust someone: it now reads "Not confirmed", names the signer, and says the site cannot vouch for them.
* Fixed: an entire explanation paragraph on review cards showed the "help" cursor as if it were hoverable — a style collision, and the question-mark cursor now appears only on the icons that actually carry a bubble.
* Fixed: the readiness card said "Everything looks good" when its advisor simply had no setup step left to suggest — a verdict it could not make, since the Cited figure above it can sit at 38% with every setup box ticked. It now says what it measured: "Nothing left to set up."
* Fixed: the Report's Citations card said "checks run on a schedule" to owners whose schedule is switched off. It now reads the schedule's real state: off means "a check runs only when you start one." And its "Open Citations" link landed on the Search tab; it now opens the Citations results it names.
* Improved: the Client Decisions rows read cleanly — a known crawler's name is no longer printed twice, the decision verb no longer repeats the tab's own name on every row, columns line up, long names shorten instead of pushing the date out of line, and on a phone each client folds to two tidy lines with a proper thumb-sized button.
* Improved: plain words on the undo buttons — "Stop trusting" and "Stop ignoring" replace the made-up "Un-trust" and "Un-ignore" — and the buttons look like buttons before you hover them, without turning red for what is a routine, reversible act.

## 1.49.0
* New: a warning that your CDN is blocking an AI company is now verified before it may keep saying so. Cloudflare counts crawlers by their User-Agent string, and anyone can wear one — so a vulnerability scanner probing for exposed files while wearing "OAI-SearchBot" was booked, blocked, as OpenAI, and the conflict card told the owner "Cloudflare is blocking OpenAI, but your policy says allow" about a company that never visited. This is the same defect the review queue shed in 1.48.0 — a spoofed population wearing the real engine's numbers — standing one layer further out, where the counts arrive pre-blended. While a blocking warning is live, the hourly poll now asks Cloudflare for the blocked traffic's source addresses (one bounded call, paid only while a conflict fires) and verifies each against what the operator publishes, with the same verifier the Request Log already trusts. When everything checked proves to be someone else, the warning stands down to a note that the edge is stopping an impersonation campaign: nothing needs allowing, and the real company is not being kept out. One verified request keeps the warning, and so does a sample that is mostly undetermined — "could not say" is never read as "not them". On the site this was built for, the first check sampled 1,029 blocked requests and every one came from outside OpenAI's published ranges.
* Improved: the demoted notice keeps everything the warning had. The derived date the blocking began, the owner's fold, the deep link to review it — all carry over, because it is the same situation better understood, not a new one. The verdict itself ages out within a day rather than lingering, so last week's sample can never explain away this week's blocking, and the notice becomes a warning again by itself the moment verified traffic starts being refused. A check that cannot run — the API refusing, the ranges unavailable — leaves the warning standing and writes its failure down rather than failing silently.
* Improved: a connected assistant reading the edge summary sees the verdict beside the conflict: how many blocked requests proved to be the company, how many proved to be impostors wearing its name, and how many could not be determined — declared in the tool's schema, so the same three-valued honesty the owner's screen shows is what a machine is told.

## 1.48.0
* New: the Request Log records what crawlers read on your pages, not only which AI files they fetched. Recording ran on four serve-paths — the generated endpoints, the .well-known documents, the discovery route and refusals — and ordinary HTML was logged nowhere, so an AI crawler could read every article on the site and the log showed nothing but its llms.txt fetch. The screen's own promise, "every visit a machine made to your site", was not true. Only machines are recorded: the test is the exact inverse of the one the visitor counter uses, so a visit is either a human referral or a machine read and never both, and your readers are never logged here. Every URL shares one address, "Page (HTML)", the way every .md twin already shares one. A page served from a CDN or a caching plugin never reaches WordPress and cannot be counted, so on a cached site these are a floor rather than a total, and the footer says so. A switch in Settings turns the whole stream off; with it off the footer says that too, because "no crawler read this article" is a conclusion and it must not be drawn from a question nobody asked.
* New: a request that arrives cryptographically signed is recorded as signed even when the signature belongs to an operator this plugin does not recognise. Web Bot Auth lets a crawler sign its requests so a site can check the sender rather than take their word for it, and Agentimus has verified those signatures for some time — but it only wrote down who signed when the signature also changed that client's standing, which happens for two operators. So a valid signature from anyone else was proved genuine and then left no trace at all: the row read "unchecked", and an owner asking whether anything had signed their site was told no by a log that had seen it. Being worthless is not the same as not having happened. The signer is now recorded independently of the verdict, and an unrecognised operator earns exactly as much standing as before, which is none.
* New: a Signature filter on the Request Log, and on the tool a connected assistant uses. It takes an operator's name and also a wildcard meaning "carried a signature at all" — the question an owner asks first, and the one no list of names can express, because you cannot pick the name of a company you have never seen. Nothing coming back is then a real answer rather than a missing feature.
* New: signed requests are also exempt from the log's write budget. Busy minutes are sampled so no single client can fill the table, and signed traffic is rare enough that the one signed request in a thousand would have been thrown away by that sampling. Only a verified signature is exempt — a failed one is cheap to manufacture in bulk, and exempting those would be a way around the budget rather than a use of it.
* New: a conflict between your CDN and your own declared AI policy now appears on the Findings list, dated. Agentimus has detected these for some time — a CDN turning away a crawler the site welcomes, or letting training crawlers through a site that asked it not to — but they appeared only on the Request Log, so an owner learned about them by walking onto that screen. On the site this was found on, one had been firing for two days and another for weeks, unseen. They are findings now: urgent when the edge is refusing an assistant the policy welcomes, because only the owner can settle that and only in someone else's dashboard; a quieter note when a declared preference simply is not being enforced. A conflict the owner hid stays hidden — a warning dismissed on one screen must not reappear on another.
* New: each conflict says when it BEGAN, derived from the hourly figures already on disk rather than from the moment the plugin first looked at it. A recorded stamp can only date a conflict from first sight, so a site installing this feature today would be told a problem that started last week started today — and on the site this was built for, that is exactly what it said. The beginning is now read out of the stored history using the same thresholds the conflict itself applies, a day at a time, so three weeks of light blocking that never crossed the bar is correctly excluded and the day the behaviour actually changed is the one reported. Where the history cannot answer, the wording changes rather than the date being invented: a derived start, "running since at least" when the condition held on every day still kept (the beginning is older than the retention, and saying otherwise would turn a retention limit into a fact), and "first seen" when there is no usable history at all. A day the poll never ran breaks nothing — silence is not evidence that a conflict stopped. They are recomputed from observed behaviour on every read and stored nowhere, so a card could say "in the last 7 days" — the window it measured — while nothing could say when the problem started. The stamp shares the dismissal record's lifecycle: it dies with the situation, so a conflict that ends and later returns is dated from its return rather than telling you a problem you fixed in March has been running since March.
* Fixed: the Findings list claimed "Nothing is blocking AI assistants" whenever every setup check passed. That is a promise the checks cannot make. They measure this plugin's own configuration, and on the site this was found on the sentence sat on the front door while the CDN turned away 3,289 of 3,466 requests from OpenAI's crawler — every check green, the configuration genuinely perfect, and the assistant still getting an error. A clear line that a card two screens away can contradict is worth less than one that never overstates, and a false all-clear is worse than no line at all because it stops the owner looking. It now says what it measured: "All N setup checks pass."
* Improved: the weekly email names any live conflict at your CDN, with the date it started. It is the only channel that reaches an owner who is not in wp-admin, and it is the one that would have caught the unseen notice weeks earlier.
* Improved: the conflict notice on the Request Log folds now instead of hiding. Hide removed the card outright and trusted you to remember what it said — and with conflicts now counted on the Findings list and named in the weekly email, one screen's tidiness would have silenced every other surface too. Only two things end a conflict: the edge changing its behaviour, or your own policy changing to match it. So the card now collapses to a single line — badge, title and the link to review it at your CDN all keeping their places — opens again with a click, and every surface keeps counting it until it actually ends. A notice you had hidden on an earlier version comes back collapsed, not gone.
* Improved: the three small scripts the plugin adds to your pages — the WebMCP bridge, the AI-referral beacon and the Focus live counter — are minified when built, cutting them from 13KB to 4.5KB. Their source moved to `resources/public/` and ships in the package beside the built files, exactly as the admin interface's Vue source always has, so there is still no minified-only code.
* Improved: the page-view stream has its own write budget rather than sharing the one the generated files use. A crawl of the content is orders of magnitude more requests than a crawl of the files — one llms.txt, then five hundred articles — so on a shared budget the new stream would have spent it and started sampling away the llms.txt and .md records this log exists to show.
* Fixed: the address filter above the Request Log offered internal names — "markdown", "rest:discovery" — while the table beside it showed the plain ones for the same rows. One screen was speaking two vocabularies; it now speaks the table's.
* Fixed: a crawler could name your own site as its home page and have the plugin fetch you on its behalf. Agentimus checks whether a crawler's self-declared home page exists, and nothing stopped that URL being yours — so any stranger could point your server at itself, and once pages were logged that self-fetch was recorded as a visit. Your own address is refused outright now; it never proved anything, because of course your own front page answers.
* Fixed: two response headers were emitted without checking whether the response had already begun, so a theme or plugin printing output early produced a PHP warning on top of its own bug. They now stand down quietly, as the third one beside them always did.
* Fixed: a crawler-review card blended an impersonator's traffic with the real engine's. One User-Agent string can carry two populations — the genuine engine, whose requests verify against what its operator publishes, and a stranger borrowing the exact same name — and the card rightly reports the worst thing it saw. But its request count and its "last seen" spanned both populations, so it could read "Failed verification · 95 requests · 5 hours ago" when the five-hours-ago request was the real Googlebot's verified visit and the last actual forgery was six days old. The numbers beside a verdict are now the verdict's own: the card counts and dates the failing requests themselves, and says separately how much verified traffic the real engine sent under the same name.
* Fixed: the list of clients awaiting review that a connected assistant reads still included clients you had already blocked, so its count could say 12 while the bell in your admin bar said 11. Two surfaces counting one thing must read one count, and now they do. Each client on that list also carries the recorded IP addresses the review advice tells you to block — the one piece of evidence the screen had and no tool exposed.
* Fixed: on hosts whose C library lowercases text byte by byte — macOS, mainly — any text in Cyrillic, Arabic, Greek or Devanagari was corrupted on its way into the search-coverage check, and every measurement of it logged a PHP warning. A non-Latin search still came out unreadable, which is the right answer arrived at wrongly; but a page merely containing such text — an English page quoting one Russian sentence, say — could have whole passages read as empty and be marked as not answering a search it answers. Lowercasing no longer consults the host: only Latin letters survive the tokeniser anyway, so ASCII case is the only case there is.
* Improved: a post's structured data now carries its featured image. The page's JSON-LD named the headline, the author and the dates — and the site's own Person node had its photo, and the video nodes their stills — but the article itself never named the one picture its author chose for it, the field Google lists as recommended for articles. It is emitted only when a featured image is set; nothing is borrowed from the body or the site identity to fill the gap.

## 1.47.0
* Fixed: on a site not written in the Latin alphabet, every page carrying a reported search was told its words answer nothing. Whether a page answers its search is measured by pulling the meaningful words out of that search and looking for them on the page — and the part that pulls the words out reads Latin letters and numbers. A search written in Cyrillic, Chinese, Japanese, Arabic, Greek or Devanagari yielded nothing to look for, and "nothing to look for" came out the far end as "none of it is on the page". So a page that answered its search perfectly was accused of answering nothing; the whole site sat on the worklist permanently, and no amount of writing could clear it. The editor compounded it by telling an owner to "add the words this page should be found for" moments after they had typed them. A search the check cannot read is now reported as exactly that — not measured, not a failure — and it asks nothing of the page.
* Fixed: a URL somebody pasted into a search box, and somebody's prompt pasted in whole, were judged against your pages like real searches. Both produce rows no edit can ever close: no writing makes a page answer a web address. Search engines report every string that showed your site, and the filter deciding which of those may judge a page only knew about search operators — the `site:` and `inurl:` probes that machines use. It now also leaves out web addresses and anything far longer than a person types into a search box.
* New: you can set a search aside, not just a page. A row saying a page does not answer its search can be true two ways: the page is lacking, or the search was never a question your site should answer. There was a way to say the first and no way to say the second — so the only lever was to set the page aside, which takes good writing off the list to quiet a bad query, and leaves that query flagging every other page it touches. The row now offers both, each beside the thing it acts on. Nothing about any page changes, nothing changes in Google, and any search you set aside can be put back from the Search screen.
* New: an assistant asked to check one page now gets the whole verdict for it. Whether a page needs work has two halves — how readable it is, and whether its words answer the search it is found for — and the per-page tool an assistant reaches for graded only the first. So a page flagged solely on the second came back a spotless fourteen out of fourteen, and an assistant told to fix it read that as nothing to do. On one real site that was true of every row on the list. It now answers both halves, says which of the searcher's words the page never uses, and gives one plain yes-or-no on whether there is work here at all.
* New: a connected assistant can set a search aside too, one at a time. It refuses any search no engine has actually reported for your site, so the list stays a record of real searches rather than a store of typed-in text, and putting one back is always allowed — an engine going quiet can never strand a decision you made.
* Improved: the list of searches left out of the Search screen now says why each one was left out — an operator probe, a web address, something too long to be typed, or one you set aside yourself. With one rule the reason could live in a footnote; with four, a list that does not name the reason per row cannot be checked, which is the only thing that list is for.
* Improved: the figure reading "N% of the views recorded on your pages weren't people" now counts machine probes alone. It had grown to cover everything left out for any reason, and a pasted web address says nothing about who typed it. The wider figure is still there, described as what it is.
* Note: your site reads its pages once after updating. What a stored reading means has changed, so every page is read again in the background, a few at a time, with the old readings on screen throughout. A finding that was true all along may appear on your list.

## 1.46.0
* New: a connected assistant can read a page and change one passage of it, instead of replacing the whole thing. Until now the only way an assistant could act on a page was to rewrite it end to end, so a two-word fix — adding a source link, splitting a long paragraph — meant handing back a whole published article reconstructed from a reading of it. It can now ask for a page's body exactly as you wrote it, and replace one passage, leaving every other character alone. The passage has to be quoted back exactly and has to appear once: not found and found-twice are both refusals that change nothing, because a fix applied to a guess is how content gets mangled.
* New: an assistant can describe a picture that has no description — the commonest thing wrong with content on most sites, and the one thing it previously could not do. It writes the sentence you would write in the media library, on an image that is already there.
* New: and it can describe the pictures inside a page, which is a different job from the one above and the reason both exist. WordPress copies an image's description into the page at the moment you insert it and never looks at it again, so the words a reader actually gets from a published page are the ones written into that page. Describing the library copy of a picture that is already published changes nothing a reader sees. There is a tool for each now, and each says plainly which copy it writes.
* New: a way to find the pictures in your media library that carry no description at all. Search matches words, and the images that need describing are exactly the ones with no words on them, so "which of my pictures have no description?" was a question nothing could answer. It is answered newest-first, and a description that is only the file name counts as no description, the same way the page checks count it.
* New: an assistant can also see, for any page, every picture in it — where each one lives, what it says now, and which ones the checks are asking about — so it can fix the right one rather than guess.
* Fixed: the tool for describing a picture refused the exact pages the checks were flagging. Where an image's description was only its file name, the check said so and asked for it to be replaced, and the tool refused it as already described — and told the assistant that the checks were satisfied. So an assistant working through your list could find those pages and close none of them, and had been told there was nothing there. The checks and the tools that fix them now share one definition of what counts as a description; a file name is not one, and never was.
* Fixed: an empty description on a captioned picture is now a finding. An empty description is the standard way of saying a picture is decoration, and that is still respected — a spacer or a divider is never flagged. But WordPress leaves that field empty by default, so "this picture means nothing" and "nobody filled this in" arrived looking identical, and a screenshot with a caption written underneath it could reach every screen reader undescribed while the row said every image had a description. A caption is the author's own evidence that a picture means something, and the two together are now reported as the contradiction they are.
* Fixed: that new check would never have run on anything you had already published. A page is only read again when the set of checks changes, and the plugin recognises that change by the checks' names and their thresholds — neither of which a new rule inside an existing check touches. So every page on every site would have kept its old reading until somebody edited it. The rule now declares itself, your site re-reads its pages once after updating, and any finding that was true all along appears.
* Fixed: captions come in three shapes and only one was understood. The block editor writes one, the classic editor writes another, and the same classic caption is drawn a third way on any theme that has not opted into HTML5 markup — a great many of them. On those sites the check either could not see the caption at all, or saw it and then had its own fix refused. All three are read now, on both sides.
* Fixed: an assistant told to describe a page's featured image was told "this page has no featured image, add one" even where the kind of content cannot have one. A product or a custom content type registered without featured-image support has no such box, and no check ever asks it for one, so that advice sent an assistant looking for something that is not on the screen. The two absences are told apart now, and the suggestion to add one appears only where it can actually be added.
* Fixed: an assistant could be handed a page it must not write to and only find out by writing. A page built by a page builder, and a post somebody has open in the editor, are both refused before anything is changed — that second one is the case where an editor left open sends an autosave minutes later carrying the body from before, silently undoing the change.
* Fixed: the two counts of your worklist could disagree with each other, and the probe that reads what your theme does with a picture's description had a gap in its filter.
* Improved: on the dashboard's Today line, how each figure compares with yesterday is a small arrow at the end of its label rather than a coloured sentence beneath it. A whole red line reading "4 fewer than yesterday" read as an alarm about a number that had moved by four, and it made every figure three lines deep. The number it moved by is still there — hover the arrow — and a figure that did not move now says nothing at all, because an arrow earns its place by saying which way.
* Improved: every write an assistant makes to a page keeps the previous version as a revision, and the saved page is read back and compared. A page the site filtered on the way in is reported as a failure naming the revision to go back to, never as a success.

## 1.45.0
* Fixed: a page could be told it does not answer a search it is no longer found for. Whether a page answers its search is measured once, in the background, against the search the engines showed it for at that moment — and the engines move that search without anybody touching the page. The reading beside it was then an answer to a different question. Pages are now read again when their search changes, and the old reading stays on screen, marked, until the new one replaces it. A connected assistant is told the same thing, so it cannot repeat a reading that has gone out of date.
* Fixed: a day Bing reported nothing about was drawn as a drop to zero pages in the index. Bing answers for every date in its window whether or not it has numbers for that date, and a date with nothing in it was stored and drawn as a measurement — a fall to zero and back, on a site that never left the index. Those days now keep their place in the chart as a gap you can hover, and say what they are when opened.
* Fixed: for the same reason, the "Pages in Bing's index" figure above that chart could have read zero — it takes the most recent day, and a day Bing said nothing about would have supplied it. It now reads the most recent day Bing actually reported.
* Fixed: the warning about Bing's crawler hitting errors could go quiet on a site that was still erroring. It stops when the most recent day is clean, and a day with no numbers in it looked clean. It now reads the most recent day Bing actually reported.
* Fixed: fresh numbers from Bing could be overwritten by an empty answer. Bing re-sends its whole window on every poll, so a day it reported properly could come back carrying nothing and replace good numbers with zeros. An empty answer can no longer overwrite a reading.
